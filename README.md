# 가공식품 영양 비교 검색 서비스

"덜 짠 간장, 당 적은 고추장 찾기"처럼 같은 종류의 가공식품을 영양성분으로 비교하고,
더 건강한 대체 제품을 추천하는 웹 서비스입니다.

> 출처: 공공데이터포털 (전국통합식품영양성분정보 표준데이터, 공공누리 제1유형 출처표시)

## 기술 스택
- Python 3.14, FastAPI, MySQL, (v2부터) Redis
- ORM/마이그레이션: SQLAlchemy 2.x (동기, PyMySQL) + Alembic
- 테스트: pytest
- 화면: Jinja2 템플릿 (FastAPI가 HTML을 직접 렌더링)
- 실행 환경: Windows, `.venv` 가상환경, Docker Compose

순서: CSV 읽기 → `corrections.csv` 보정 → 필요한 칼럼만 정리 → 값까지 같은 중복 합치기 → 저장

- 식품코드를 기본키로 두고 `INSERT ... ON DUPLICATE KEY UPDATE`로 저장 → **다시 실행해도 중복이 생기지 않고 새 값으로 덮어씀**
- 전체를 한 트랜잭션으로 저장 → 중간에 실패하면 전부 되돌려서 반쯤 들어간 상태가 남지 않음
- `corrections.csv`의 원래값이 지금 데이터와 다르면 멈춤 → 데이터를 새로 받은 뒤 엉뚱한 값을 덮어쓰지 않게
- 알려진 한계: 새 CSV에서 사라진 제품은 DB에서 지워지지 않음

### 웹 화면 (Jinja2 템플릿)
API와 같은 함수(`search_products`, `compare_products`, `find_alternatives`)를 쓰고, 결과를 HTML 템플릿(`app/templates/`)으로 보여줍니다.

| 주소 | 화면 |
|---|---|
| `/?q=간장&target=category&page=1` | **검색어 칸 하나** + 찾을 곳 선택(제품 이름 / 대표식품명 / 회사 이름) + **상세 조건**(기준량, 칼로리·나트륨·당류·포화지방 이하를 **드래그바**로) + 결과 목록(**한 번에 5·10·20·30개** 중 선택, 기본 20, 이전·다음 쪽은 조건과 개수를 유지). 검색어가 없으면 검색창만 |
| `/products/{식품코드}` | 상세: 기준량당 영양성분 4개, 같은 종류 비교 링크, **나트륨이 더 낮은 제품 5개**, **당류가 더 낮은 제품 5개**. 없는 제품은 404 화면 |
| `/compare?category=간장&basis=100ml&sort=sodium&size=20` | 같은 종류 비교: 나트륨·당류·포화지방 중 고른 값 낮은 순, 정보 없는 제품은 맨 뒤. 한 번에 5·10·20·30개 선택 |

- 모든 화면 아래에 **"출처: 공공데이터포털"** 표시 (공공누리 출처표시 조건)
- 화면 검색은 칸 하나로 통합 (2026-11-12): 결과 목록에 대표식품명이 보이므로 입력 칸을 나누지 않음
  - 제품 이름: 이름에 검색어가 들어간 제품 전부 (`간장` → 3,489건, 간장게장·장아찌간장 포함)
  - 대표식품명: 정확히 같은 종류만 (`간장` → 829건). 참치 → 참치김밥이 섞이지 않게 하는 원래 규칙 유지
  - 회사 이름: 제조사(없으면 수입사)에 검색어가 들어간 제품
  - API는 그대로 `q`(+`target`)와 `category`를 따로 받아서 둘을 함께 쓸 수 있음
- 화면 표기는 "에너지" 대신 **"칼로리"**, "업체" 대신 **"회사"** (API 필드 이름 `energy_kcal`, `maker`는 그대로)
- 상세 조건은 드래그바(`<input type="range">`, 라이브러리 없음). 범위는 100g·100ml당 칼로리 0~900kcal(10씩)·나트륨 0~8,000mg(100씩)·당류 0~100g(1씩)·포화지방 0~50g(0.5씩)이고 **맨 오른쪽은 제한 없음**. 끄는 동안 옆에 지금 값("5,000 mg 이하" / "제한 없음")을 보여주는 짧은 스크립트만 씀
- 드래그바는 맨 오른쪽이어도 값을 보내므로, 화면 쪽은 글자로 받아 `parse_limit`으로 바꿈: 비었거나 숫자가 아니거나 **맨 오른쪽 값 이상이면 조건 없음**. 그래서 정보 없는 제품이 빠지지 않고 쪽 링크에도 안 붙음. 그보다 큰 값(예: 나트륨 10,000mg 이하)은 API의 `max_sodium`으로는 쓸 수 있음. 조건을 하나라도 넣으면 상세 조건 칸이 펼쳐진 채로 보임
- 영양값 표시는 필터 하나(`format_nutrient`)로: NULL은 **"정보 없음"**(0과 구분), 숫자는 천 단위 쉼표 + 불필요한 소수점 0 제거 (6454.00 → 6,454 mg, 0.40 → 0.4 g)
- 제품 이름은 자동 이스케이프되어 `<script>` 같은 글자가 HTML로 실행되지 않음
- 휴대폰 폭(375px)에서도 페이지는 옆으로 밀리지 않고, 넓은 표만 옆으로 스크롤
- 디자인: CSS 라이브러리 없이 `base.html`의 `<style>` 하나로 만듦
  - 색은 `:root` 변수 한 곳에서 정하고, 다크 모드는 `prefers-color-scheme`로 같은 변수만 바꿈
  - 카드형 구성, 상세는 영양성분 4칸 타일(휴대폰에서는 2칸)
  - 비교·추천 표는 **정렬·추천 기준이 된 칸을 강조**(`.hl`)
  - "정보 없음"은 흐린 색(`.na`)으로 표시
  - 첫 화면에 대표식품명 예시(간장, 고추장 등) 바로가기
  - 글꼴은 Google Fonts의 Noto Sans KR (못 불러오면 시스템 글꼴)

### 제품 검색 API
`GET /api/products?q=샘표&target=maker&category=간장&basis=100ml&max_sodium=5000&page=1&size=20`

| 파라미터 | 내용 |
|---|---|
| `q` | 검색어. 이름(또는 회사 이름) 어디에든 들어 있으면 찾음 (결과는 `LIKE '%q%'`와 같고, 2글자 이상 낱말이면 FULLTEXT 인덱스로 빠르게). `%`, `_`도 글자 그대로 찾음 |
| `target` | 검색어를 찾을 곳: `name`(제품 이름, 기본) / `maker`(회사 이름 = 제조사, 없으면 수입사) |
| `category` | 대표식품명 정확히 일치. 종류는 이름이 아니라 이 값으로 거름 (참치 → 참치김밥이 섞이지 않게) |
| `basis` | 기준량 `100g` / `100ml` (선택) |
| `max_kcal`, `max_sodium`, `max_sugar`, `max_sat_fat` | 상세 조건: 칼로리(kcal)·나트륨(mg)·당류(g)·포화지방(g)이 **이 값 이하**인 제품만 (기준량당 값, 0 이상) |
| `page`, `size` | 쪽 번호(1부터), 한 쪽 개수(1~100, 기본 20) |

- `q`와 `category`가 둘 다 비어 있으면 **400** (조건 없이 33만 건 전체를 정렬하지 않게)
- 상세 조건을 넣은 영양값이 **정보 없음(NULL)인 제품은 빠짐**: 조건에 맞는지 알 수 없으므로. SQL에서 `NULL <= 값`이 참이 아니라 조건만으로 빠짐
- 잘못된 `target`·`basis`, 음수 상한은 **422**
- 정렬: 이름순, 이름이 같으면 식품코드순 (쪽을 넘겨도 순서가 바뀌지 않게)
- 응답: `total`(전체 건수), `page`, `size`, `items`(식품코드, 이름, 업체, 대표식품명, 기준량, 영양값 4개, 정보 없으면 `null`)

```json
{"total": 71, "page": 1, "size": 2, "items": [
  {"food_code": "P112-004000400-0098", "name": "1.6자연숙성양조간장", "maker": "성심마스타푸드",
   "category": "간장", "basis": "100ml", "energy_kcal": 64.0, "sodium_mg": 6454.0, "sugar_g": 0.4, "sat_fat_g": 0.0}, ...]}
```

### 제품 상세 API
`GET /api/products/{식품코드}` (예: `/api/products/P107-113011300-0051`)

- 식품코드(기본키)로 한 건을 찾아 검색 결과와 같은 모양으로 돌려줌: 이름, 업체, 대표식품명, **기준량**, 영양값 4개
- 영양값이 없으면 `null` (실제 0과 구분), 없는 식품코드는 **404**

```json
{"food_code": "P107-113011300-0051", "name": "라코니코 엑스트라 버진 올리브 오일",
 "maker": "Our Family’s Olive Oil LLC", "category": "올리브유", "basis": "100g",
 "energy_kcal": 840.0, "sodium_mg": 0.0, "sugar_g": 0.0, "sat_fat_g": 13.33}
```

### 같은 종류 비교 API
`GET /api/compare?category=간장&basis=100ml&sort=sodium&page=1&size=20`

| 파라미터 | 내용 |
|---|---|
| `category` | 대표식품명 (필수) |
| `basis` | `100g` 또는 `100ml` (필수). **기준량이 다르면 비교하지 않음** |
| `sort` | 낮은 순으로 정렬할 값: `sodium`(기본) / `sugar` / `sat_fat` |
| `page`, `size` | 검색과 같음 |

- 정렬: 고른 영양값 낮은 순 → 같으면 이름 → 식품코드
- **값이 없는(NULL) 제품은 맨 뒤.** MySQL은 오름차순에서 NULL을 맨 앞에 두므로 `ORDER BY sodium_mg IS NULL, sodium_mg`로 정렬 (`IS NULL`은 값이 있으면 0, 없으면 1)
- 응답: 검색 응답 + `category`, `basis`, `sort` (어떤 묶음을 무엇으로 정렬했는지)
- 실제 데이터 확인: 액상커피 100ml 2,342건 중 나트륨 정보 없는 5건이 마지막 쪽 맨 뒤에 옴

### 대체 제품 추천 API
`GET /api/products/{식품코드}/alternatives?by=sodium&limit=10`

| 파라미터 | 내용 |
|---|---|
| `by` | 무엇이 더 낮은 제품을 찾을지: `sodium`(기본) / `sugar` |
| `limit` | 보여줄 개수 1~50 (기본 10) |

- 후보: 기준 제품과 **대표식품명·기준량이 같고**, 고른 값이 기준 제품보다 **확실히 낮은** 제품 (`sodium_mg < 기준값`)
- **당류로 찾을 때는 나트륨이 기준 제품보다 높은 제품을 뺌** (`sodium_mg <= 기준 나트륨`). 당은 줄었는데 더 짜지면 건강한 대체가 아니기 때문
  - 나트륨이 정보 없음인 후보는 더 짜지 않다고 말할 수 없어서 빠짐
  - 기준 제품의 나트륨이 정보 없음이면 비교할 값이 없어 이 조건은 걸지 않음
  - 실제 데이터: 1.6자연숙성양조간장(당류 0.4g, 나트륨 6,454mg)의 당류 대체가 110건 → 59건, 나트륨 10,700mg 제품이 빠짐
- 정렬: 고른 값 낮은 순 → 같으면 이름 → 식품코드
- **정보 없음(NULL) 처리**
  - 후보의 값이 NULL이면 제외 (SQL에서 `NULL < 값`은 참이 아니라 조건만으로 빠짐)
  - 기준 제품의 값이 NULL이면 "더 낮다"고 말할 수 없으므로 빈 목록 (`total: 0`)
- 응답: 기준 제품(`product`), `by`, 더 낮은 제품 전체 수(`total`), 목록(`items`). 없는 식품코드는 **404**

```json
{"product": {"food_code": "P112-004000400-0098", "name": "1.6자연숙성양조간장", "sodium_mg": 6454.0, ...},
 "by": "sodium", "total": 506,
 "items": [{"name": "미트벨리불고기간장", "basis": "100ml", "sodium_mg": 1168.0, "sugar_g": 4.9, ...}, ...]}
```

실제 데이터에서 본 점 (v1은 그대로 두고 기록만):
- 같은 '간장' 안에 불고기 간장 같은 양념형 간장도 있어서, 낮은 순 맨 앞에 용도가 다른 제품이 나올 수 있음

- 화면은 같은 API 함수를 써서 검색·비교는 API와 거의 같음(템플릿 렌더링 시간은 작음). **상세 화면은 추천을 나트륨·당류 두 번 불러와 테이블을 4번 읽어서 약 0.5초** → v2에서 가장 많이 줄어야 할 곳

- 결과가 8건이든 9,683건이든 **약 250~290ms로 거의 같음** → 결과 수가 아니라 테이블 전체를 읽는 시간이 대부분
- `EXPLAIN`: 세 쿼리 모두 `type=ALL`(전체 32만 행 읽기), 정렬이 있는 목록 쿼리는 `Using filesort`. 요청 한 번에 전체 건수(COUNT)와 목록 쿼리로 **테이블을 두 번** 읽음
- 상세는 기본키(식품코드)로 바로 찾아서 14ms → 검색이 느린 이유는 DB 크기가 아니라 **찾을 인덱스가 없어서**임을 보여줌
- v2에서 볼 것: 대표식품명 인덱스(필터·정렬), 한글 이름 검색(FULLTEXT ngram, `LIKE '%q%'`는 일반 인덱스를 못 씀), 전체 건수 캐시

### v2 1단계: (대표식품명, 기준량, 영양값) 인덱스 (2026-11-12)
비교·추천·대표식품명 검색은 모두 `category = ? AND basis = ?`로 **한 묶음만** 보는데, 인덱스가 없어 32만 행을 다 읽고 있었습니다. 그래서 (대표식품명, 기준량)을 앞에 두고 그 묶음 안에서 낮은 순으로 찾는 영양값을 세 번째에 둔 인덱스를 3개(나트륨·당류·포화지방) 만들었습니다.

- 세 번째 칼럼이 영양값인 이유: 추천의 `sodium_mg < 기준값`처럼 묶음 안에서 범위로 찾을 때 인덱스로 바로 좁힘(`type=range`)
- 대표식품명만으로 찾을 때도 인덱스 앞쪽(category)만 써서 탐 (왼쪽부터 쓰는 복합 인덱스 규칙)
- 이름 검색(`LIKE '%간장%'`)은 앞이 `%`라 일반 인덱스를 못 써서 그대로 → 2단계 FULLTEXT에서 다룸

같은 날 같은 방법으로 인덱스 추가 **직전에 다시 잰 값**과 비교 (중앙값):

| 경우 | 인덱스 없음 | 인덱스 추가 후 | 변화 |
|---|---|---|---|
| **화면: 상세 (추천 2개 포함)** | 466ms | **30ms** | **약 15배** |

`EXPLAIN` (간장 100ml):

| 쿼리 | 전 | 후 |
|---|---|---|
| 비교 목록 | `ALL` 324,247행 + filesort | `ref` 750행 + filesort |

- **상세 화면이 가장 많이 빨라짐**: 테이블 전체를 4번 읽던 것이 간장 묶음(수백 행)만 4번 읽게 됨

### v2 2단계: 이름·회사 이름 FULLTEXT ngram 인덱스 (2026-11-13)
`LIKE '%간장%'`은 앞이 `%`라 일반 인덱스를 못 써서 32만 행을 다 읽습니다. MySQL FULLTEXT 인덱스를 **ngram 파서**로 만들면 글자를 2글자씩 잘라(양조간장 → 양조·조간·간장) 색인해서, 이름 중간에 든 검색어도 인덱스로 찾습니다 (alembic `0003`).

**결과를 LIKE와 똑같이 맞춘 방법** (`app/search.py`의 `text_condition`)
- `MATCH(name) AGAINST('"간장"' IN BOOLEAN MODE) AND name LIKE '%간장%'`: 큰따옴표는 구문 검색(글자가 이어져 있는 것). FULLTEXT로 후보를 빠르게 좁히고, LIKE로 한 번 더 확인
  - FULLTEXT만 쓰면 부호·띄어쓰기 차이로 더 찾는 경우가 있음 (실제 데이터: `Coca-Cola` 회사 LIKE 13건 / FULLTEXT 32건, `100%` 3,228건 / 3,233건) → LIKE를 함께 걸어 해결
- FULLTEXT를 쓰는 검색어는 **글자·숫자 2개 이상인 낱말을 띄어쓰기로 이은 것**만 (`[^\W_]{2,}( [^\W_]{2,})*`). 한 글자(`김`)나 부호로 끊겨 2글자가 안 되는 것(`1.6`, `(주)`)은 색인에 없어 FULLTEXT로는 0건 → **LIKE로만** 찾음
- 검증: 실제 제품 이름·회사 이름에서 무작위로 자른 검색어 **1,000개**(이름 500, 회사 500)에서 LIKE와 결과 수 차이 **0건**

**정한 것 / 알게 된 것**
- **불용어 끄기**: MySQL 기본 불용어(a, i, in 등 영어)가 켜져 있으면 ngram은 불용어가 든 2글자 토큰을 색인에서 뺌 → `ICHIBIKI` 같은 영어 이름을 못 찾음. 마이그레이션에서 `SET SESSION innodb_ft_enable_stopword = OFF` 후 인덱스를 만듦 (인덱스를 만드는 순간의 설정이 적용됨)
- **대표식품명이 있으면 FULLTEXT를 안 씀**: 처음엔 `q=고추장&category=고추장`이 23ms → 101ms로 **느려짐**. MATCH가 있으면 MySQL이 FULLTEXT 인덱스를 먼저 골라 이름에 '고추장'이 든 2,043건을 읽음(대표식품명 인덱스로는 627건). 대표식품명이 있으면 LIKE만 쓰게 바꿔 22ms로 돌아옴
- 정렬은 관련도가 아니라 지금처럼 이름순 (`Ft_hints: no_ranking`)

같은 방법으로 잰 중앙값:

| 경우 | 인덱스 없음 (v1) | 1단계 후 | **2단계 후** |
|---|---|---|---|
| 이름 검색 (결과 많음, `간장` 3,489건) | 263ms | 269ms | **78ms** |
| 이름 검색 (결과 적음, `라코니코` 8건) | 261ms | 264ms | **17ms** |
| 이름 검색 50쪽 | 268ms | 270ms | **85ms** |
| 회사 이름 검색 (`샘표` 84건) | 262ms | 297ms | **19ms** |
| 화면: 검색 (`간장`) | 267ms | 364ms | **79ms** |
| 이름 + 대표식품명 | 236ms | 23ms | 22ms (FULLTEXT 안 씀) |
| 한 글자 검색 (`김` 14,514건, LIKE) | - | - | 347ms (전체 읽기, 그대로) |

- 결과가 많을수록 시간이 듦(간장 78ms vs 라코니코 17ms): 찾은 행을 LIKE로 확인하고 이름순 정렬하는 일이 결과 수만큼 늘어남
- `EXPLAIN` 이름 검색: `ALL` 324,247행 → `fulltext` (`ft_products_name`)
- 대가: 인덱스 만들기 33초, FULLTEXT 보조 테이블 약 43MB + 숨은 칼럼(`FTS_DOC_ID`)으로 데이터 44.6 → 53.6MB, 다시 적재 22.4초(1단계 후 24.2초와 비슷, 측정 흔들림 범위)
- 테스트 시간: 테스트마다 마이그레이션을 다시 하던 방식이 FULLTEXT 때문에 46초 → 115초로 늘어서, 마이그레이션은 한 번만 하고 테스트마다 `TRUNCATE`로 바꿈 (76개 56.9초)

### v2 3단계: Redis 캐시 (2026-11-13)
검색·비교·추천 결과(응답 모양 그대로의 pydantic 모델)를 JSON으로 Redis에 저장해, 같은 조건의 요청은 DB를 읽지 않고 꺼냅니다 (`app/cache.py`). API와 화면이 같은 함수(`search_result`·`compare_result`·`alternatives_result`)를 써서 캐시도 같이 씁니다.

| 정한 것 | 이유 |
|---|---|
| 키: `nutri:종류:{조건 JSON}` (`sort_keys=True`) | 조건이 같으면 같은 키. `nutri:` 머리말로 이 앱 키만 골라 지움 |
| **적재가 끝나면 비우기** (`cache.clear()`) + **TTL 1시간** | 데이터는 적재 스크립트로만 바뀌므로 거기서 바로 비우는 게 주된 방법. 비우는 걸 잊어도(예: DB를 직접 고침) 1시간 안에 새 결과가 나오게 TTL을 안전장치로 (사용자와 결정) |
| 지울 때 `SCAN` (`KEYS *` 안 씀) | `KEYS`는 키가 많으면 Redis를 잠깐 멈추게 함. `FLUSHDB`는 같은 DB의 다른 데이터까지 지움 |
| **Redis가 꺼져 있으면 DB로** | 캐시는 빠르게 하려는 것이지 없으면 안 되는 것이 아님. 연결 대기 0.5초 제한 |
| 상세(식품코드)는 캐시 안 함 | 기본키로 이미 빠름(약 14ms). 상세 화면의 추천 2개는 캐시 |

같은 날 연속으로 잰 중앙값 (`--no-cache`: 20번 모두 DB / 캐시 켬: 미리 1번 실행해 저장한 뒤 20번은 캐시에서):

| 경우 | v1 (인덱스 없음) | 2단계 후 (캐시 없음) | **캐시 적중** |
|---|---|---|---|
| 이름 검색 (`간장` 3,489건) | 263ms | 111ms | **9.6ms** |
| 한 글자 검색 (`김`, LIKE) | - | 366ms | **9.9ms** |
| 대표식품명만 (큰 종류 기타 빵) | 231ms | 81ms | **10ms** |
| 같은 종류 비교 (큰 종류) | 278ms | 96ms | **10ms** |
| 같은 종류 비교 (간장) | 224ms | 23ms | **9.1ms** |
| 대체 제품 추천 (기타 빵, 당류) | 296ms | 78ms | **16ms** |
| 화면: 검색 | 267ms | 80ms | **12ms** |
| 화면: 상세 (추천 2개 포함) | 466ms | 31ms | **17ms** |
| 제품 상세 (기본키, 캐시 안 함) | 13ms | 14ms | 15ms |

- 캐시 적중은 결과 수·쿼리 종류와 상관없이 **약 9~17ms로 고름**. 기본키 상세(14ms)와 비슷하므로 이 정도가 앱(FastAPI·JSON 변환) 자체 시간이고, DB 시간은 거의 사라짐
- 추천·상세 화면은 기준 제품을 기본키로 한 번 읽은 뒤 캐시를 봐서 16~17ms
- **인덱스로 이미 빨라진 곳(간장 비교 23ms)은 차이가 작고, 인덱스로 못 줄인 곳(한 글자 검색 366ms, 큰 종류 80~96ms)에서 효과가 큼**
- 캐시가 없는 첫 요청은 2단계와 같은 시간 (그래서 1·2단계 인덱스가 여전히 필요)
- 적재 확인: 캐시 키 14개 → 적재 후 0개 (`적재 완료: 324763건, …, 캐시 N개 비움`)
- 테스트 정리: 테스트마다 `TRUNCATE`하던 것이 FULLTEXT 보조 테이블까지 다시 만들어 1~2초씩 걸려서 `DELETE`로 바꿈 → 전체 테스트 91초 → **10.5초**

**동기 → 비동기 전환 판단 (v2 목표 중 하나)**: 캐시 없이도 대부분 20~110ms, 캐시 적중 시 약 10ms이고, 남은 시간 대부분이 DB 대기가 아니라 앱 자체 처리라 **비동기로 바꿔서 얻을 것이 작음** → 동기 유지. 동시 접속이 많아져 DB 대기가 쌓이는 상황이 측정되면 다시 판단.
